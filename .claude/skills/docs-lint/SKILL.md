# docs-lint

`docs/`の内容が、今のコード(`Assets/Supplement`・`Assets/Supplement.MessagePack`・`Assets/Supplement.ZeroMessenger`)と食い違っていないかを点検し、**コードを正として**ドキュメントを直す。
ドキュメントの構成と書き方のルールは`CLAUDE.md`の「ドキュメント(Wiki)」に従う。

## 範囲

- 引数が無ければ、`docs/`のすべてのページを点検する
- 引数にページ(`save-data.md`)や機能・型の名前(`BackKeyReceiver`)があれば、そのページと、それに関係するコードだけを点検する

## 手順

### 1. 読む

- `docs/`のページをすべて読む(範囲を絞ったときは、対象のページと`index.md`・`getting-started.md`・`changelog.md`の未リリースの節)
- 対象のコードを**すべて**読む。XMLドキュメントコメントではなく、実装を読む。コメントもドキュメントと同じくずれていることがある
- `package.json`(バージョン・依存)と`.asmdef`(アセンブリ名・名前空間・`versionDefines`・`noEngineReferences`)も読む

### 2. 突き合わせる

ページごとに、次の観点で食い違いを探す。

| 観点 | 例 |
|---|---|
| 型・メンバー | 消えた型・メソッドが載っている。公開しているのに載っていない主な型・メソッド |
| シグネチャ | 引数・戻り値・ジェネリックの制約・既定値の違い |
| 名前空間・アセンブリ | ページ冒頭の「アセンブリ・名前空間」、`using`の要否 |
| 動き | 順序・並列か・何もしない条件・既定値・上限(リトライの回数など) |
| 例外 | 投げる例外の型と条件。例外を投げずにログに出すだけのもの |
| DIへの登録 | 拡張メソッドの有無と、登録している型 |
| コード例 | 存在しないAPI、古いシグネチャ。書いてある通りに使うと動きが変わるもの(既定の設定が外れるなど) |
| 依存 | `getting-started.md`の依存パッケージ・バージョンと`package.json` |
| 変更履歴 | `changelog.md`の未リリースの節と、実際の差分(`git diff main`)。消した型を「移動」と書いていないか |
| リンク | 消えたページへのリンク、`#見出し`へのリンク(使わない) |

- 主張は1つずつコードで確かめる。数値や出力の例(CRCの値など)は、計算して確かめる
- 迷うものは、実装を読み直してから判断する。推測で直さない

### 3. 直す

- **ドキュメントだけを直す。コードは変えない。** コードの方がおかしいと思ったものは直さず、報告に分けて書く
- 直すときは`CLAUDE.md`のルールに従う
  - 利用者向けのページには、使う人に必要なこと(使い方・動き・制約)だけを書く。内部クラスの名前・実装の仕組み・テストの話は`maintainers/`に書く
  - 同じことを複数のページに書かない。ほかのページにあることはリンクで示す
  - 機能のページには今の動きだけを書く。経緯は`changelog.md`に書く
  - ページ間のリンクはページ単位にする
- ドキュメントだけの修正は`changelog.md`に足さない
- 改行コードは元のファイルに合わせる(LF)

### 4. 報告する

- 直したところを、ページごとに「誤りだった記述」と「書いていなかった動き・制約」に分けて挙げる
- コードの方が怪しいもの(ドキュメントの方が意図に合っていそうなもの、`package.json`の古い依存など)は、直さずに別に挙げる
- コミットはしない。ユーザーに聞く
