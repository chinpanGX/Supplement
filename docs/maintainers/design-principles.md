# 設計の方針(メンテナー向け)

機能を足す・変えるときに、何を選び、何を選ばないかの基準をまとめます。個々の実装の仕組みと理由は[内部の設計](internals.md)に、GCアロケーションの方針は[パフォーマンスとGC](performance.md)に書きます。

## 全体

- 速さは、使いやすさを保てる範囲で追います。APIの形・例外の扱い・注入のしかたが変わる高速化は、速さの得と使いやすさの損を並べてから決めます。使い方を変えない案を先に検討します
- ベンチマークで勝つことを目的にしません。数値は、選んだ設計が遅くないことを確かめるために測ります

## MessageBroker

- 役目は、最小限のpub/subです。外部ライブラリに依存せず、注入するのは`IMessageBroker`の1つだけで、非同期はUniTaskで扱います
- ZeroMessengerより機能が多いことは目指しません。比べるときは「機能を絞っても、速さとGCアロケーションは同等以上」であることを示します([ベンチマーク](benchmark.md))
- 次の機能は意図して持ちません
  - フィルター(ハンドラーの前後に処理を挟む仕組み)。使う場面がほとんど無いため
  - 完了を待つ発行(`PublishAsync`)。理由は[内部の設計](internals.md)
  - R3などほかのライブラリとの連携。ZeroMessengerとの連携(`GlobalMessageBroker`)も非推奨にし、今後のバージョンで削除します
- 型ごとのインターフェース(`IMessagePublisher<T>`・`IMessageSubscriber<T>`など)で受け取る形は取りません。注入を1つに保つためです。インターフェースのジェネリックメソッド(`IMessageBroker.Publish<T>`など)を通す呼び出しのコスト(.NETで1回あたり約3ns)は、そのための必要なコストとして受け入れます
